让一次语音输入，始终只发生在一个地方

今天 10:366 分钟阅读自动保存

真正自然的语音输入，不应该要求用户理解内部经历了多少次转写、多少次模型调用。界面需要承认系统仍有状态，但不能把这些状态变成不断跳转的空间。

顶部面板更像一张临时铺开的工作纸：内容从上向下生长，结果稳定后直接落进当前文档。它不抢走焦点，也不要求用户停下来管理工具本身。

当文本变长，空间应服务于阅读；当它遮挡工作区，又应能在一次动作后收成细窄的信息条。可靠感来自持续、克制和可预期。

原文 实时转写

我觉得这一次可以先不要急着实现，我们先把整个交互聊清楚。现在最主要的问题是，软件虽然已经有实时优化了，但是我停止以后，界面还是会从大面板切换成一个小胶囊，然后再告诉我正在润色。这个过程从系统内部看也许是合理的，但是从使用者的角度看，它其实像是同一件事被做了两次。 我希望录音、实时转写、实时优化、最后收尾和插入，都在同一个面板里面完成。停止以后，如果最后一点尾音还没有被模型处理，就让面板留在原位继续完成，不需要突然变成另一种形态。正常完成后直接插入，再给一个很轻的成功反馈就可以了。 另外长文本也是一个问题。我有时候会一次说五六百字，现在的宽度和行距看起来会比较挤。把面板放到顶部以后，内容可以自然地往下增长，而且原文和优化稿最好能一直左右对照，这样我可以直观看到模型改了什么。 还有，调用耗时我也希望在顶部看到，因为我有时会切换不同模型，希望能直观知道每一次实际请求用了多久。这个时间不要把录音或等待停顿算进去，只算请求发出到完整结果返回。如果第一次调用失败，错误区域保留这次耗时，重试的时候重新计时，这样我才好判断到底是网络偶发问题，还是模型本身速度不稳定。 最后，整个面板即使展开得很高，也不要在里面再套滚动区域，因为那样我还是得用鼠标去找前面的内容。我宁愿它覆盖当前窗口，需要时自己点收缩。还有一点，如果模型调用失败，希望不要直接把面板关掉，最好保留原文，并且给我一个手动重试优化的按钮。

这次先不急于实现，优先把整体交互讨论清楚。 当前的核心问题是：虽然软件已经支持实时优化，但停止录音后，界面仍会从大面板切换为小胶囊，并再次提示“正在润色”。从系统内部看，这可能对应不同处理阶段；但从用户视角看，同一件事像是被重复执行了两次，体验并不连贯。 更自然的方案，是让录音、实时转写、实时优化、最终收尾和文本插入都发生在同一个面板中。用户停止录音后，如果仍有尾音尚未处理，面板就在原位完成最后一次收敛，不再切换为另一种容器。处理完成后直接插入文本，并在原面板内给出短暂、克制的成功反馈。 长文本的可读性也需要同步改善。一次输入五六百字时，现有宽度、字号和行距会显得拥挤。将面板移动到屏幕顶部后，内容可以自然向下增长；展开状态采用原文与优化稿的左右对照布局，既能持续确认识别结果，也便于观察模型具体修改了哪些内容。 当面板遮挡当前应用时，用户可以手动将其收缩为顶部信息条。收缩只改变显示体积，不中断录音或优化；应用本次运行期间继续记住这一选择。 标题栏还需要展示真实的 LLM API 耗时，方便比较不同提供商和模型。计时应从请求实际发出开始，在完整响应返回或失败时结束，不应混入录音时长、停顿等待或缓存复用时间。首次调用失败后，错误区域保留该次调用的模型、状态与耗时；手动重试则开启一次新的独立计时。这样既能判断单次网络异常，也能持续观察模型速度是否稳定。 为了保持免鼠标的体验，展开面板内部不再设置滚动容器。即使面板占据大部分屏幕，也应把约六百字内容完整铺开；遮挡当前应用时，由用户主动收缩成顶部标题条，而不是把阅读成本转移给滚动操作。
